## Resolution update

The confirmed implementation findings in this review were subsequently fixed:

- runtime `0d7a31041` aligns per-camera transforms and task-specific camera
  routes, OD anchors/decoding/NMS, buffer ownership, engine contracts and error
  propagation, and builds the independent core plus `lidar_obj_det`;
- profile `8c3b21a5d` carries the matching camera routes, preprocessing and OD

- MapTR/export `f72fb84` prevents stale TensorRT plan reuse by recording and

The historical findings below are retained as review evidence; they no longer
describe open code defects. Numerical parity, recorded-data replay and final
target-engine validation remain deferred by user direction.

## Scope and result

Reviewed runtime commit `089b4ec8a`, profile commit `ced8d14a2`, and export
commit `312071d`. This was a code review and targeted compilation/CPU contract
check, without model inference on recorded data, training, or playback.

The independent module boundary is a reasonable foundation, but the current
implementation is **not ready for deployment acceptance**. Previous syntax
checks covered the core rather than the complete algorithm. The findings
below supersede any interpretation that the complete runtime was validated.
No runtime, export, or profile implementation was changed during this review.

Runtime paths below are relative to `src/perception_q`; training paths are
relative to `code/maptr`. Profile paths are relative to `src/profile_project`.

## Confirmed findings

### P1 — Algorithm does not compile

`include/lidar_obj_det/lidar_obj_det/dl_bevfusion_mapod/dl_bevfusion_mapod.h:22`
includes `mapod_common/common.h`, which does not exist. The original
`common/common.h` is a project-wide header under
`include/dl_runtime/commons/common/common.h`, not the copied CUDA common
directory. A mechanical rename changed this unrelated include.

Confirmed by compiling `dl_bevfusion_mapod.cpp` with `g++ -fsyntax-only`
inside `baize-welldriver-wviz-1`, using the existing lidar_obj_det CMake include
flags plus the new module include directories. Compilation stops at this
missing header. Fix the include or remove it if unused, then compile the whole
algorithm and factory/node integration rather than just the core.

### P1 — Image preprocessing and geometric projection disagree

`src/lidar_obj_det/lidar_obj_det/dl_bevfusion_mapod/dl_bevfusion_mapod.cpp:784`
hardcodes the augmentation matrix to scale `(0.48, 0.48)` and translation
`(0, -3)`. The normalizer computes its own crop from configurable dimensions
in `src/dl_runtime/dl_bevfusion_mapod/CUDA-BEVFusion/src/bevfusion_mapod/camera-normalization.cu`.

For the committed profile (960x540 input, 704x256 output, scale 0.48), the
normalizer calculates resized dimensions 460x259, crop `(-122, 3)`. Its
geometric translation must therefore be `(+122, -3)`, not `(0, -3)`. This is an
internal inconsistency independent of any unverified camera calibration.

The MAP top-middle camera also requires the training pipeline's
`letterbox_width` mode: resize to 528x256 and pad 88 pixels on either side.
The new runtime implements only one common isotropic resize/bottom crop.
It does not implement that per-camera policy. Training uses PIL crop padding;
the copied CUDA border sampling does not implement the same black padding.

`load_images` also passes only raw pointers and does not check cv::Mat shape,
type or stride. The normalizer copies a fixed byte count per camera. Restore
metadata checks before accepting camera buffers.

Fix by deriving both pixel processing and `img_aug_matrix` from one
per-camera transform description, including raw-stream/calibration scaling,
crop/padding, and channel order. Do not independently tune the matrix.

### P1 — OD anchor geometry differs from the selected checkpoint

`project/cnwxijk/qthd/perception_q/79-perception.yaml:237` has different anchor
sizes from both the executable training config and the saved training dump:

| Class | Training size | Runtime profile size |
| --- | --- | --- |
| Car | [4.5, 1.8, 1.5] | [4.5, 2.0, 1.6] |
| Vehicle | [10.0, 2.8, 3.2] | [13.0, 3.0, 3.4] |
| IGV | [15.5, 3.2, 3.2] | [3.4, 1.9, 2.8] |

The CUDA decoder also uses edge-aligned coordinates with divisor `size - 1`.
Training uses `AlignedAnchor3DRangeGenerator(align_corner=False)`. CPU
execution of the actual generator gives the first x/y anchor at
`(-53.7, -53.7)`; the CUDA formula gives `(-54, -54)`.

The z convention needs to match the native generator plus
`DeltaXYZWLHRBBoxCoder.decode`: native anchors use z=3 for the configured
range, and the coder explicitly converts between bottom and center. The
runtime instead derives its z reference from half the anchor height plus
zero bottom heights. A unified comparison must account for these different
stages rather than comparing z numbers as if they had identical semantics.

Relevant code:
`src/dl_runtime/dl_bevfusion_mapod/CUDA-BEVFusion/src/mapod_postprocess/postprocess_kernels.cu:50`;
training `mmdet3d/core/anchor/anchor_3d_generator.py:289` and
`mmdet3d/core/bbox/coders/delta_xyzwhlr_bbox_coder.py`.

Fix by extracting anchor and decoding contracts from the selected config and
comparing native/C++ zero-delta and nonzero-delta examples on CPU or synthetic
tensors. Tensor shapes alone cannot establish decoding equivalence.

### P1 — OD output allocation and count are unsafe

`src/dl_runtime/dl_bevfusion_mapod/CUDA-BEVFusion/src/mapod_postprocess/postprocess.cpp:354`
allocates `(anchor_count * 7 + 1)` floats. The active CUDA kernel writes
9 floats per detection at `postprocess_kernels.cu:103`, without a capacity
guard. Sufficient accepted anchors therefore overflow the allocation.

The kernel writes `bndbox_output[0] = resCount + 1` from multiple threads.
Atomic allocation of `resCount` does not order these separate stores; a lower
count may overwrite a higher one. Moreover, that element is not initialized
before a zero-detection frame, and the host reads it instead of the separately
initialized atomic `object_counter_`.

Fix the record stride/capacity, read the atomic counter after stream completion,
validate the count, and cover both zero detections and capacity-limit cases.

### P1 — OD suppression no longer matches offline evaluation

`postprocess.cpp:429` performs NMS over all classes together. `nms_cpu` does
not check class labels, so boxes of different classes suppress each other.
The native `mmdet3d/core/post_processing/box3d_nms.py:52` filters and performs
NMS separately for every class.

The deployed decoder also keeps only the best class for each anchor; native
multiclass processing retains qualifying class candidates. The profile sets
score/NMS thresholds to 0.5/0.1 versus native 0.3/0.2, and the declared
`nms_pre_maxsize` is not used as a candidate cap. Separate intentional product
threshold tuning from faithful baseline decoding; implement native semantics
first to permit meaningful comparison.

### Model-contract issue — Four-camera union changes the inference input

The actual configured task sets are:

- OD: FRONT_MID + FRONT_MID_LEFT + FRONT_MID_RIGHT;
- MAP: FRONT_TOP_MID + FRONT_MID_LEFT + FRONT_MID_RIGHT.

The exporter defaults to four cameras and the runtime pools all four into one
BEV before feeding both heads. Sharing learned weights does not imply that
features from different camera sets are equal. This union path is a new
deployment candidate, not a faithful reproduction of either task-specific
three-camera evaluation. Accuracy loss is possible but has not been measured;
the review does not claim that adding a fourth camera is necessarily harmful.

For a faithful initial deployment, retain one independent module and one set
of weights, share camera feature extraction and LiDAR features where inputs
and preprocessing are identical, then pool the two camera subsets separately
and execute the shared fuser/decoder weights for each route. This costs extra
BEV computation. A single four-camera BEV remains an optimization requiring
its own validation or camera-aligned training.

## Additional robustness gaps

- Namespace isolation is incomplete: the new sparse parser still defines
  `spconv::load_engine_from_onnx`, some CUDA kernels remain in global scope,
  and ONNX generated protobuf symbols are duplicated. Shared third-party
  spconv use is fine; module-owned parser/helper symbols should be isolated.
  Header coexistence does not prove dynamic-library symbol independence.
- Only the MAP head validates the full engine binding contract. Camera, OD,
  vtransform and fuser paths assume expected dtypes/shapes. Engine enqueue
  failure is ignored in several paths; `run_maptr`'s boolean is ignored by
  the caller. `Anchor3DImplement` also has output pointers without default
  initialization, making early-load failure cleanup unsafe.
- `build_shared_bev_multitask_engine.sh:52` skips any existing plan solely by
  filename, then replaces the sparse ONNX/plugin/manifest. Reusing an output
  directory with changed input artifacts can produce a mixed-model bundle.
  Validate provenance before skipping, or require a fresh bundle directory.

## Checks that did succeed

- The pointcloud output helper and the TensorRT wrapper, OD postprocess C++,
  YAML parser, and sparse parser pass syntax checks in the deployment container.
- Previously checked MAP head/core syntax is not contradicted; it was simply
  insufficient to establish whole-module compilation or runtime correctness.
- The exported fuser ONNX contains 14 `InstanceNormalization` nodes from the
  GroupNorm export path. There is no evidence here that GN was simply removed;
  this structural check does not establish numerical TensorRT parity.
- No existing `dl_bevfusion` implementation files were changed by the runtime
  commit. The new pipeline remains non-default in the profile.

## Recommended order

1. Resolve whole-module compilation, count/allocation bugs and failure handling.
2. Match native anchors, bbox decode, and multiclass NMS.
3. Unify per-camera image transforms and geometric matrices.
4. Preserve task-specific camera routing for the correctness baseline.
5. Harden bundle provenance and module symbol isolation.
6. Build/link the complete module. Run recorded-data/numerical comparisons only
   when the user resumes that validation phase; it remains deferred here.
